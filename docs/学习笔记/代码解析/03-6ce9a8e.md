一句话：**把 Toolset 范围从「结果后过滤」下推进搜索引擎的候选查询，并把「请求从哪个入口来」（Root/Toolset Scope）持久化进 Execution 和 Audit**。全程零数据库 Migration。

## Why：为什么做这个

I03-3（上一个提交）留了两个明确债务，[实验记录 43](file:///e:/AI_Projects/LearnProjects/Projects/NexusAI/NexusMCP/docs/实验记录/43_I03-3_ScopedMCPEndpoint.md) 自己承认了：

**债务一：搜索是「结果后过滤」。** 上一个提交里 `_filter_search_result` 只在返回边界按 Toolset 过滤。这在排序后过滤有一个经典陷阱：

```
用户在 5 个成员的 Toolset 里搜索
检索阶段：全租户候选 → 组外 Tool 相似度 0.98、0.97、0.96 占据 Top-3
LIMIT 5 截断 → 组内最高分 0.85 被截掉
结果后过滤 → 组内 Tool 全部消失 = 召回不足
```

**债务二：审计回答不了「从哪进的门」。** 整体规划验收标准第 6 条要求「一次请求可以查看跨 Registry、Policy、Upstream 和 Audit 的 Trace」，但当时 ToolExecution 和 Audit 都不记录 Scope——管理员无法回答「这次调用是通过哪个 Toolset 入口授权的」。

另外还有一个隐性动机：**成本护栏**。无授权 Agent 的搜索不应该触发付费的 SiliconFlow Embedding 调用，所以空范围必须在调用 Provider 之前短路。

## How：关键实现决策

### ① 三态字段 `eligible_tool_ids: tuple[str, ...] | None`

这是整个提交最精妙的设计：

| 值 | 语义 | 行为 |
|---|---|---|
| `None` | Root 入口，无 Toolset 限制 | 查询不带 `IN (...)` 过滤 |
| `()` 空元组 | Toolset 入口但可见集合为空 | **直接返回空，不查库、不调 Embedding** |
| `("id1", "id2")` | 限定成员集合 | SQL `ToolModel.id IN (...)` |

为什么必须是三态而不是「空集合 = 无限制」？因为**「不限制」和「限制为空集」是两种完全不同的授权结论**，用普通集合无法区分（空集天然歧义）。`None` 和 `()` 的区分让 Root 语义和 Deny 语义各自显式。

### ② 服务端注入，Schema 不可见

[server.py](file:///e:/AI_Projects/LearnProjects/Projects/NexusAI/NexusMCP/src/nexusmcp/interfaces/mcp/server.py) 里用 `dataclasses.replace(query, eligible_tool_ids=...)` 在 Handler 内注入，来源是已鉴权的 `ResolvedToolsetAccess.available_tool_ids`。这个字段**不出现在 Meta Tool 的 JSON Schema 里**——Agent 在协议上无法指定或扩大范围。这是信任边界：过滤参数属于服务端授权结论，不属于客户端输入。

### ③ 下推位置：Coverage 和 Candidate 双 SQL + LIMIT 之前

[sqlalchemy_vector_search.py](file:///e:/AI_Projects/LearnProjects/Projects/NexusAI/NexusMCP/src/nexusmcp/modules/tool_search/adapters/sqlalchemy_vector_search.py) 里 `IN (...)` 同时加在 Eligible Coverage（计数）和 Candidate（候选）两条语句上，FTS 同理。于是：

```
过滤发生在 排序 和 LIMIT 之前
→ 组外高分 Tool 根本不进候选池
→ RRF 融合时词法/向量两路都只见成员
→ Top-K 名额全留给组内
```

但**保留了一次结果边界的 ID Filter 作为纵深防御**（belt and suspenders）——下推是性能与召回优化，边界过滤是正确性兜底，防止未来某条新搜索路径忘记带 Scope 时泄露。

### ④ 拒绝审计：事前、摘要、白名单错误码

[_record_scope_denial](file:///e:/AI_Projects/LearnProjects/Projects/NexusAI/NexusMCP/src/nexusmcp/interfaces/mcp/server.py) 只对 4 个稳定错误码（`toolset_not_found/not_active/access_denied/member_unavailable`）触发，发生在 ToolExecution 创建**之前**。审计内容刻意极简：

```python
arguments_digest=canonical_json_digest(dict(params.arguments or {}))  # 只存 sha256 摘要
# 不存原始 Arguments、Result、Authorization、Token、Credential
```

而 `tools/list` 和正常搜索**不写持久化审计**，只产生结构化 Log/Trace——这是噪声控制：读操作高频，写审计会把 Audit 表变成日志表。

### ⑤ 双理由码分离

`policy_reason_code`（Tool Policy 判定，如 `read_only_allowed`）保持不动，Toolset 访问理由放在 `metadata.scope_reason_code`。两个独立的授权决策（「这个 Principal 能不能用这个 Tool」vs「这个请求从哪个授权入口进来」）各答各的，组合起来才构成完整证据链。

### ⑥ 零 Migration

复用既有 `tool_execution` 的 Scope 列（领域不变量 `ToolExecution.__post_init__` 里早就有校验——说明**当初建表时就预判了 Scope，这次只是把管道接通**）和 `audit_event.metadata` JSON 列。领域不变量还抽成了共享的 `_validate_mcp_scope()`：ROOT 不得带 toolset 字段、TOOLSET 必须同时带 id 和正 revision，命令对象和实体复用同一条规则。

## Trade-off：付出了什么

| 决策 | 得到 | 失去 / 风险 |
|---|---|---|
| **下推 + 保留后过滤** | 正确性有兜底，防新路径泄露 | ❌ 双重过滤的微小开销；两处逻辑要同步演化 |
| **审计 Scope 放 metadata JSON** | 零 Migration | ❌ 「查某 Toolset 的全部调用」不能走索引列，要靠 JSON 操作符；好在此查询频率低，且 Execution 表有正规列 |
| **拒绝审计内联 await** | 拒绝事件与响应同步落库 | ⚠️ **若审计写库失败，异常会向上传播、遮蔽原始 MCP 错误**——这是本提交最值得警惕的点。更稳的做法是 try/except + 降级为日志（当前测试没覆盖审计库故障场景） |
| **4 个错误码硬编码白名单** | 噪声可控、语义明确 | ❌ 新增 Scope 错误码时必须记得同步这个集合，否则新拒绝静默漏审 |
| **`_scope_metadata` 写了两份** | approval 与 execution 解耦 | ❌ [approval/use_cases.py](file:///e:/AI_Projects/LearnProjects/Projects/NexusAI/NexusMCP/src/nexusmcp/modules/approval/use_cases.py) 用字符串 `"toolset"` 字面量而非枚举，两份逻辑可能漂移 |
| **空范围短路** | 省钱、语义清晰 | ❌ 搜索行为分叉（快空 vs 真查），文档必须讲清楚；测试已覆盖 |

## Alternative：被放弃的方案

1. **继续结果后过滤**（I03-3 现状）→ 放弃：Top-K 名额被组外占据，组内召回不可接受，这是本次的核心动机。
2. **为 Audit Scope 加专用列 + Migration** → 放弃：`metadata` JSON 够用，Scope 的强查询需求落在 Execution 表（那里有正规列）。
3. **把 `eligible_tool_ids` 暴露给 Agent Schema** → 放弃：客户端可伪造扩大范围，破坏授权模型；服务端注入是唯一正确姿势。
4. **拒绝也写成失败的 ToolExecution** → 放弃：从未执行的调用不该产生 Execution 行（污染执行统计与幂等键空间）；DENIED 审计才是正确载体。测试验证「Fake Upstream 只收到一次真正允许的请求」就是这个语义的验收。
5. **把 Scope 编译进 FTS 查询串/Embedding 过滤** → 放弃：`IN (uuids)` 是最简单且必然正确的下推，全文检索层面的花活收益不成比例。

## Interview Question：面试官会怎么问

**Q1: 「为什么搜索过滤必须在 LIMIT 之前？后过滤差在哪？」**
要点：Top-K 截断是零和的——组外高分项占据名额，组内项被挤出候选，后过滤后组内召回趋近于零。正确姿势是把 Scope 作为 Candidate Query 的谓词（`IN (...)`），让排序和 LIMIT 只见过合法候选；再提 RRF 双路融合会让这个问题放大（两路各自的 Top-K 都被污染）。

**Q2: 「`eligible_tool_ids` 为什么是 `None | () | (...)` 三态？」**
要点：「无限制」和「限制为空」是不同授权结论。普通集合的空值歧义会静默把 Root 语义变成 Deny-all（或反之）。可选类型的三态是把这个业务区分编码进类型系统——类型即文档，编译器/类型检查器（basedpyright 0 errors）逼你处理每一态。

**Q3: 「拒绝审计为什么在 Execution 创建之前？为什么只存摘要？」**
要点：审计要回答「谁试图做什么、为什么被拒」，不需要执行细节。摘要（canonical JSON + sha256）满足可追责（同参数可比对）且零泄露——直接呼应项目验收标准「Credential 不进入 Audit 明文」。事前持久化是因为拒绝的调用没有 Execution 行，事后再审就没载体了。

**Q4: 「如果审计库挂了，用户的工具调用会怎样？」**
要点（主动指出上面标 ⚠️ 的风险会加分）：当前 `_record_scope_denial` 内联 await，审计失败异常会传播、遮蔽原始错误——拒绝审计对拒绝请求是**可用性耦合**。改进方向：审计写入包 try/except 降级为结构化日志（审计是尽力而为的诊断面，不是请求正确性的组成），或者审计走异步队列。这是一个诚实的已知债。

**Q5: 「没有任何 Migration，Scope 怎么落库的？」**
要点：I03-1 建 `tool_execution` 表时就预建了 Scope 列并写了领域不变量（但当时没有生产者）——这是「schema 先行、管道后通」的渐进式交付。说明数据模型设计时预判了路线图，本次只是把调用链接上。反面教训是 `scope_reason_code` 的推导逻辑在 approval 和 execution 各写了一份，应该上提到 shared。

**Q6: 「怎么证明 RRF 没有跨 Toolset 泄露？」**
要点：集成测试用真实 pgvector 构造「组外最相似向量」，断言它无法进入 RRF 融合、最终结果只含成员（实验记录 44 的验证证据列表）；同时 Coverage Count 也受 Scope 限制，排除「计数泄露」这种次级泄露。泄漏测试必须构造攻击性数据（组外分数最高），而不是用自然分布碰运气。

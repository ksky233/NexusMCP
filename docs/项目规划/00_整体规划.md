# 00｜NexusMCP 整体规划

> 状态：初步规划
> 作用：定义问题、边界、目标架构和项目完成标准。

## 1. 项目问题

当多个 Agent 分别接入企业 API、数据库、SaaS 和 MCP Server 时，通常会出现：

- 同一 Tool 被不同团队重复封装；
- API Key/OAuth Token 分散在 Agent 进程或配置文件；
- Tool 缺少统一 Owner、Version、Health 和发布状态；
- `tools/list` 结果缺少可控的发现与权限过滤；
- 有副作用的 `tools/call` 被错误重试；
- 无法回答谁、以哪个 Agent 身份、调用了什么 Tool；
- OpenAPI 服务进入 Agent 生态时缺少安全审核和发布流程；
- MCP 旧版 Session 时代与新版 Stateless 时代共存，兼容边界不清。

NexusMCP 的目标是提供统一能力出口：

```text
                     NexusMCP
        ┌────────────────────────────────┐
        │ Registry / Catalog             │
        │ Protocol Compatibility         │
        │ OpenAPI Import                 │
        │ Tool Search                    │
        │ Identity / Policy              │
        │ Credential Injection           │
        │ Approval / Audit               │
        │ Health / Trace / Metrics       │
        └───────────────┬────────────────┘
                        │
                        ▼
              Enterprise HTTP/OpenAPI
```

## 2. 项目叙事

项目对外叙事统一为：

> NexusMCP 将企业已有 HTTP/OpenAPI 服务转化并发布为受治理 MCP Tool，在调用链上执行身份解析、Tool
> Policy、Credential Injection、Approval、Audit 和 Trace，并同时兼容现代无状态 MCP 与旧版会话型
> Client。

Remote MCP Federation/Proxy 已由 ADR-0017 延后。当前不治理开发者个人 MCP，不声称透明代理全部 MCP
Capability；只有出现明确组织级 Remote MCP Upstream 后才重新评估。

不使用以下表述作为主叙事：

- “MCP Server 聚合器”；
- “MCP 转发接口”；
- “把 Swagger 转成 Tool”；
- “支持很多接口的管理后台”。

上述只是功能片段，不是项目差异化。

## 3. 现有资产

### 3.1 旧 Java 项目

`LearnForNexusAI/AI-MCP-Gateway/` 提供：

- Java/Spring Boot DDD 分层示例；
- JSON-RPC、SSE、Streamable HTTP 课程材料；
- `initialize`、`tools/list`、`tools/call` 旧版调用链；
- Gateway、Auth、Tool、Protocol Mapping 数据表；
- OpenAPI/Swagger 解析；
- Redis Session 同步；
- 管理端和部署示例。

它是重要的业务与旧协议参考，但不是新项目的 Transport 基线。具体复用规则见 [02｜Java 旧项目利用与 Python 迁移](./02_Java旧项目利用与Python迁移.md)。

### 3.2 个人已有项目经验

已有 AgentRuntime、LangChain/LangGraph 和真实上线项目经验，因此 NexusMCP 不再承担“证明会做 Agent Loop”的职责。项目只需要提供一个很薄的 Demo Client/Agent 来验证 Tool 调用链。

### 3.3 支付 MCP 经历的使用边界

易宝支付实习中的支付业务 MCP 半成品项目可以提供幂等、副作用、权限和审计方面的问题域经验，但 NexusMCP 不以支付系统作为主 Demo，也不绑定任何单一行业。

公司源码、真实业务数据和内部协议不得迁入本项目。只允许使用脱敏后的通用架构结论，并通过与原系统无关的 clean-room 实现验证。

## 4. 目标架构

第一版是一个部署单元中的模块化单体：

```text
                         NexusMCP

            ┌──────────── Control Plane ────────────┐
            │ HTTP Upstream Registry                │
            │ Tool Catalog / Search                 │
            │ OpenAPI Import / Publish              │
            │ Policy / Credential Configuration     │
            └─────────────────┬──────────────────────┘
                              │ read published snapshot
            ┌─────────────────▼──────────────────────┐
Client ────>│ Data Plane                             │
            │ Protocol Router / Auth / Context       │
            │ Tool Resolve / Policy / Credential     │
            │ Proxy / Execute / Normalize            │
            │ Trace / Metric / Audit                 │
            └─────────────────┬──────────────────────┘
                              │
                    Enterprise HTTP/OpenAPI
```

“Control Plane / Data Plane”是代码和状态边界，不代表第一版必须拆成两个服务。

## 5. 核心请求链

```text
MCP Request
  ↓
Protocol Version / Method Routing
  ↓
Agent Service Authentication → Internal Principal
  ↓
Server / Tool Resolution
  ↓
Visibility + Policy Decision
  ├── DENY → normalized error + audit
  ├── REQUIRE_APPROVAL → pending approval
  └── ALLOW
        ↓
Credential Reference Resolution
        ↓
Tool Execution / Upstream Proxy
        ↓
Response Normalization / Redaction
        ↓
Trace + Metric + Audit
        ↓
MCP Response
```

身份主线采用 Service-Centric Boundary：

```text
Admin Operator → /admin
Agent Service Principal → /mcp
Employee → Agent/业务系统（不进入 NexusMCP）
```

独立 Agent 部署使用固定 `static_service`；多个 Agent 共用时使用机器 Credential 或 Trusted Proxy 映射
Service Principal。Admin Auth 与 MCP Auth 独立配置，详见 ADR-0019。

## 6. 当前主线范围

### 6.1 必须形成闭环

- MCP `2026-07-28` 现代请求；
- 旧版客户端兼容测试；
- HTTP Upstream Registry；
- Tool Catalog 与关键词/FTS 搜索；
- OpenAPI Import → Draft → Publish；
- `tools/list` / `tools/call`；
- Agent Service Principal；
- `ALLOW / DENY / REQUIRE_APPROVAL`；
- Credential Reference / Injection；
- Audit Event；
- OpenTelemetry Trace / Metrics；
- 三个轻量、异构的 Local-first OpenAPI Demo（员工目录、运维服务、库存系统）；
- 一个内建 `nexus.search_tools` Meta MCP Tool，支持 Lexical/Hybrid Tool Retrieval；
- Golden Cases、协议测试、安全测试和 Benchmark。

### 6.2 明确不做

- 完整 Agent Runtime；
- NexusGate / NexusLLM；
- 所有 MCP Extension；
- 自研 OAuth Authorization Server；
- 完整 Secret Manager；
- 大型管理前端、拖拽式 Tool/Workflow Builder；
- 完整企业知识库/RAG平台；
- 为架构图而拆微服务；
- 支持几十种 SaaS 和 Transport；
- 企业员工注册、登录、角色、会话和行为追踪；
- 接收或保存 Agent 会话中的最终员工标识；

## 7. 项目完成的证据

项目完成不以 TODO 清零判断，而以以下证据判断：

1. 新旧协议行为可以通过自动化测试解释；
2. 三个异构 OpenAPI 服务可以通过同一条通用链路导入、审核、发布并被 Agent 调用；
3. 不同 Agent Service Principal 对同一 Tool 得到不同 Policy Decision；
4. Credential 不进入 Agent Context、普通日志或 Audit 明文；
5. 副作用 Tool 的 Retry/Idempotency 行为可说明、可测试；
6. 一次请求可以查看跨 Registry、Policy、Upstream 和 Audit 的 Trace；
7. Lexical/Vector/Hybrid Tool Retrieval 有小型评测集；
8. README、Architecture、ADR、Threat Model、Quick Start 和 Demo 可独立使用；
9. 所有性能数字附带环境、数据规模和测试方法；
10. 能明确说明旧 Java 项目哪些设计被继承、哪些被拒绝。

多源 Demo 的额外约束：

- NexusMCP 核心代码不得包含员工、运维或库存场景分支；
- 场景差异只能来自 OpenAPI、Tool Metadata、Tool Binding、Policy 和 Credential 配置；
- 接入第三个 Demo 时不得新增场景专用 Gateway/Executor；
- 每个 Fake API 保持 2～3 个接口，不建设完整业务系统。

# NexusMCP 单机生产部署规划

> 状态：D0～D5 已完成，D6 正式 Release 待执行
> 目标：将 NexusMCP 作为公开可交互的求职演示与低流量单机服务部署到现有腾讯云服务器  
> 目标域名：`nexusmcp.dearloom.me`  
> 目标环境：OpenCloudOS 9、`linux/amd64`、Docker Compose V2

## 1. 背景与规划制定时的缺口

DualStruct 已跑通以下基础设施：

- 腾讯云单机 Docker Compose；
- `dearloom.me` 与 `*.dearloom.me` 的 Let's Encrypt 通配符证书；
- Cloudflare DNS-01、Certbot Deploy Hook 与自动续期；
- Windows 本地 Buildx 构建 `linux/amd64` Image；
- `docker save → SHA256SUMS → scp → docker load` 离线发布链；
- Unprivileged Nginx、非 Root Backend、Health Check、日志轮转与手工回滚。

本规划制定时，NexusMCP 已有 Production-like Web Image，但还不是可以直接上线的生产包：

- 没有 Backend Production Dockerfile；
- 当前 `docker-compose.yml` 只编排本地 PostgreSQL；
- Web Nginx 仍通过 `host.docker.internal:8000` 访问开发机 Backend；
- Local Admin 使用固定开发身份，并被 Settings 明确禁止在 `production` 开启；
- 当前只有 Development Local Admin，尚未组装显式的 Production Public Demo 身份；
- `nexusmcp.dearloom.me` 当前由 DualStruct Edge Nginx 返回占位页。

因此部署不是简单上传现有 Web Image，而是先补齐 Production Packaging、身份入口和独立 Compose。

## 2. 目标拓扑

```text
Internet :80/:443
        ↓
Existing dearloom.me Edge Nginx
TLS termination / Host routing
        ↓ nexusmcp.dearloom.me
NexusMCP Web Nginx :8080
├── React SPA
├── Public Demo identity binding
├── /admin/* → backend:8000
├── /health/* → backend:8000
└── /mcp     → backend:8000
                       ↓
                NexusMCP Backend
                ├── PostgreSQL 18 + pgvector
                ├── SiliconFlow Embedding API
                └── Demo HTTP Upstreams
```

NexusMCP 使用独立 Compose Project、独立数据 Volume 和独立环境变量文件。现有 Edge Nginx 只负责 TLS 和 Host
路由，不拥有 NexusMCP 业务状态。

| 决策项 | 第一版决定 |

| 部署目标 | 现有腾讯云 OpenCloudOS 9 单机 |
| CPU 架构 | `linux/amd64` |
| 编排 | Docker Compose V2，不引入 Kubernetes |
| 域名 | `nexusmcp.dearloom.me` |
| TLS | 复用现有 Apex + Wildcard 证书和 Certbot 续期链 |
| Edge | 复用现有 80/443 Edge Nginx，通过共享 External Docker Network 转发 |
| 应用形态 | Web、Backend、PostgreSQL 分容器，仍是一个模块化单体部署 |

| Tenant | 单企业/单作品集 Tenant，由部署 Bootstrap 显式创建 |

### 3.2 Public Demo 身份设计

本次公网部署的主要目的，是让 HR 或面试官点击简历链接后直接体验项目。它没有真实企业 Upstream、真实业务
用户或生产数据，因此不在访问入口增加没有实际保护价值的共享账号密码。

公开访问统一映射为两个诚实命名的 Demo 身份：

```text
Browser → public-demo-admin
MCP Client → public-demo-agent
```

所有访客共享同一 Admin Principal 和同一套 Demo 数据；Audit 只表达 Demo 环境中的操作事实，不声称能够识别
具体访客。Tenant 仍由部署配置固定，不接受客户端自报 `tenant_id`。

配置方向：

```ini
NEXUSMCP_ENVIRONMENT=production
NEXUSMCP_ADMIN_IDENTITY_MODE=public_demo
NEXUSMCP_DEMO_ADMIN_PRINCIPAL_ID=public-demo-admin
NEXUSMCP_MCP_IDENTITY_MODE=static_service
NEXUSMCP_STATIC_AGENT_PRINCIPAL_ID=public-demo-agent
```

`public_demo` 必须是显式部署模式，不能通过在公网继续使用 `development + Local Admin` 假装完成生产部署。
真实企业部署仍使用 `AdminAuthenticator + Trusted Proxy/SSO`，但不在本次求职 Demo 中实现。

### 3.3 上线前容量与基础设施检查

在编写 Compose 前记录服务器事实：

```bash
uname -m
docker version
docker compose version
docker compose ls
docker stats --no-stream
free -h
df -h
ss -lntp
docker network ls
/usr/local/bin/certbot certificates
systemctl list-timers dualstruct-cert-renew.timer
```

第一版暂定 Go/No-Go 条件：

- CPU 架构为 `x86_64/linux/amd64`；
- 80/443 仍只由现有 Edge 占用；
- 空闲磁盘至少保留约 10 GiB，用于 Image、PostgreSQL、Release 与备份；
- 观察实际容器占用后，仍能为 NexusMCP Backend、PostgreSQL 和 Web 留出约 1.5 GiB 运行余量；
- Wildcard 证书覆盖 `nexusmcp.dearloom.me` 且自动续期正常；
- DNS 仍指向目标服务器；
- 现有 DualStruct 服务具备可验证的回滚点。

这些数值是本次单机部署的保守 Gate，不是 NexusMCP 的通用最低配置。若内存不足，优先调整现有服务资源与
部署拓扑，不通过增加 Swap 掩盖持续内存压力。

## 4. 第一轮｜Production Packaging 与本地编排

### D1｜Production Packaging

新增或调整：

- Backend Multi-stage Dockerfile；
- Python 3.12、Frozen `uv.lock`、非 Root UID；
- Production Web Nginx 配置，将 Upstream 改为 `backend:8000`；
- Production `.env.example`；
- Build、Export 与 Checksum 脚本；
- Image 使用 Git SHA 不可变 Tag。

### D2｜Production Compose

生产 Compose 至少包含：

```text
postgres
backend
web
demo-upstreams
```

`demo-upstreams` 使用同一 Backend Image 和一个 Uvicorn 进程，将 Employee Directory、Operations 与
Inventory 分别挂载到三个 URL 前缀；不为每个轻量场景启动独立 Python 容器。

要求：

- PostgreSQL 使用 `pgvector/pgvector:0.8.6-pg18-trixie`；
- PostgreSQL 与 Backend 只 `expose`，不发布公网端口；
- Web 通过内部 Network 访问 Backend，并接入共享 Edge Network；
- Migration 是显式部署步骤；
- 配置 Health Check、启动依赖、日志轮转、资源限制和 `no-new-privileges`；
- Production Egress Allowlist 只允许批准的 Demo/企业 Upstream 与端口；
- `.env`、数据库数据和 Secret File 不进入 Git。

第一轮验收：在全新本地 Volume 中，Production Compose 可以完成 Migration、启动、Health Check 和容器间
代理；暂不切换公网域名。

## 5. 第二轮｜Demo 身份与初始化

### D3｜Public Demo 身份组装

- 增加显式 `public_demo` Admin Identity Mode；
- 将公开 Web 请求映射为固定 `public-demo-admin`；
- MCP 使用现有 `static_service` 映射为固定 `public-demo-agent`；
- 保持 `development` Local Admin、公开 Demo 和未来真实 Production Admin 三种语义分离；
- 保持 Admin 与 MCP 两条身份链分离。

### D4｜Migration、Bootstrap 与 Demo 数据

- 执行 `alembic upgrade head`；
- 幂等创建 Tenant，并从 Settings 组装固定 Demo Admin/Agent Principal；
- 文档提供三个 Demo Upstream 的内部 Endpoint，由访客在 Web 中完成注册；
- Import OpenAPI、Review、Publish Tool；
- 调用 SiliconFlow 生成 Tool Embedding；
- 增加“重置演示工作区”Admin Use Case 与 Web 按钮；
- 重置只清理 NexusMCP 业务数据并恢复固定 Tenant/Demo Principal，不删除 Schema、Migration 或 PostgreSQL
  Extension；
- 重置后可以重新演示 `Create Upstream → Import → Review → Publish → Search → Call`；
- 该 Endpoint 只在 `public_demo` 模式注册，不作为通用生产数据库管理能力。

## 6. 第三轮｜本地生产演练与 Release

### D5｜Clean Production Rehearsal

从全新 Volume 执行：

```text
Build linux/amd64 Images
→ Start Compose
→ Migration
→ Bootstrap
→ Browser/Admin/MCP 验收
→ Restart
→ Persistence 验收
```

### D6｜Release Bundle

生成：

```text
nexusmcp-images.tar
docker-compose.yml
production config templates
deployment scripts
SHA256SUMS
```

Release 不包含 Provider Key、数据库密码、Admin 密码、Agent Token 或证书私钥。

## 7. 第四轮｜服务器发布与域名切换

### D7｜Server Deploy 与 Edge Cutover

- 上传到 `/opt/nexusmcp`；
- 校验 SHA256 并 `docker load`；
- 创建独立 Volume 与共享 External Edge Network；
- 先只在服务器内部验证 NexusMCP Web；
- 将 `nexusmcp.dearloom.me` 从占位页切换到 NexusMCP Web；
- `nginx -t` 成功后 Reload；
- 保留可以立即恢复占位页的配置和旧 Image Tag。

现有 Wildcard 证书和 Certbot Timer 继续由 Edge 统一维护，不在 NexusMCP 内复制一套证书生命周期。

### D8｜正式验收

至少验证：

- HR/面试官打开域名后无需登录即可进入 Web；
- Admin Audit 使用共享 `public-demo-admin`，MCP Execution 使用共享 `public-demo-agent`；
- PostgreSQL 与 Backend 无公网监听；
- Upstream → Import → Publish → Search → Call → Audit 全链路；
- `tools/list` 同时包含内建 Meta Tool 与已发布业务 Tool；
- Lexical 与 Hybrid Tool Search 正常；
- `demo_directory.get_employee` 可以通过 MCP 调用；
- SSRF Metadata 地址与非 Allowlist Upstream 被拒绝；
- 容器重启后数据保持；
- Log、响应和 Release Artifact 不泄露 Secret。

### D9｜运维、备份与回滚

- PostgreSQL 定期 `pg_dump`；
- 至少完成一次空库恢复演练；
- 记录 Health、Log、Disk、Memory 与证书检查命令；
- Web-only 更新不重建 PostgreSQL；
- Image 通过上一个 Git SHA 回滚；
- Image 回滚与 Schema/Data 回滚分开处理。

## 8. 明确不在本轮完成

- Kubernetes、Multi-Region 与自动扩缩容；
- 企业 OIDC/SSO Provider 的具体 Adapter；
- NexusMCP 自建员工注册登录和复杂 RBAC；
- 本次求职 Demo 的 Trusted Proxy/OIDC Admin Adapter；
- Managed PostgreSQL、Vault/KMS 和完整 CI/CD Registry；
- 将开发数据库原样上传到服务器；
- 为了部署而拆分现有 Domain 或改造成 Microservices。

## 9. 实施顺序

```text
D0 冻结与检查
→ D1 Backend/Web Production Packaging
→ D2 Production Compose
→ D3 Production Identity
→ D4 Bootstrap
→ D5 Clean Rehearsal
→ D6 Release Bundle
→ D7 Server Deploy
→ D8 Acceptance
→ D9 Operations
```

只有 D0 的容量和边界 Gate 通过后才进入服务器变更；D1～D6 均先在本地完成，不影响现有 DualStruct 服务。

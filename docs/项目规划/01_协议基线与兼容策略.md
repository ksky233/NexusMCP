# 01｜MCP 协议基线与兼容策略

> 状态：已确认的协议方向，具体 SDK API 在项目初始化时锁定版本后复核。
> 核心原则：现代协议优先、旧协议兼容、协议时代显式可观测。

## 1. 当前协议基线

NexusMCP 以 MCP `2026-07-28` 为现代主线。

该版本相对旧版的关键变化包括：

- 移除 `initialize/initialized` handshake；
- 移除协议级 `Mcp-Session-Id`；
- 每个请求通过 `MCP-Protocol-Version` 和 `_meta` 自描述；
- 提供可选 `server/discover`；
- Streamable HTTP 使用 `Mcp-Method`、`Mcp-Name` 等 Header 支持网关路由；
- list/read 结果支持 `ttlMs`、`cacheScope` 等缓存提示；
- 使用 Multi Round-Trip Requests 处理需要补充输入的调用；
- Tasks 进入 Extension；
- 旧的 Roots、Sampling、Logging 等能力进入弃用路径；
- 使用 W3C Trace Context 传播 Trace；
- OAuth/Authorization 进一步加强 issuer、audience 和客户端元数据安全。

官方说明：<https://blog.modelcontextprotocol.io/posts/2026-07-28/>

## 2. 两个协议时代

| 维度 | Legacy Era | Modern Era |
|---|---|---|
| 主要版本 | `2025-11-25` 及更早 | `2026-07-28` |
| 生命周期 | `initialize` handshake | 每个请求自描述，可选 `server/discover` |
| Session | 可使用 `Mcp-Session-Id` | 无协议级 Session |
| 水平扩容 | 可能需要 sticky/shared session | 普通负载均衡即可路由任意实例 |
| Server → Client | 依赖连接/回调能力 | MRTR / Extension / Subscription 机制 |
| Gateway 路由 | 常需解析 JSON body | 可利用 `Mcp-Method`、`Mcp-Name` |
| List 缓存 | 客户端自定义 | 标准缓存提示 |

NexusMCP 不把两种时代揉成一个隐式分支。每次请求必须解析出：

```text
protocol_version
protocol_era = modern | legacy
transport
method
name/resource（如适用）
```

这些字段进入 RequestContext、Trace 和 Audit。

## 3. 版本协商策略

### 3.1 Server 侧

推荐使用官方 Python MCP SDK v2，在同一应用入口上：

- 对 `2026-07-28` 请求进入 Modern handler；
- 对旧客户端 `initialize` 进入 Legacy handler；
- 不自行重写完整 JSON Schema 和 Transport；
- 对未知 Method 返回规范化 method-not-found，不返回模糊 500；
- 每个协议版本建立独立 Golden Cases。

### 3.2 Client 侧

NexusMCP 内部测试 Client 采用：

```text
auto negotiation
  ↓ server/discover
modern supported → modern
method not found / old server → legacy initialize fallback
```

另提供显式 pin 模式，用于协议测试：

```text
modern-only
legacy-only
auto
```

### 3.3 依赖锁定

项目初始化时记录：

- Python SDK 版本/commit；
- 支持的协议版本；
- Conformance Suite 版本；
- 已知 expected failures；
- Legacy fallback 行为。

不要使用“latest”作为不可复现的依赖声明。

## 4. 现代请求入口

现代请求进入 Data Plane 时，先验证：

```text
MCP-Protocol-Version
Mcp-Method
Mcp-Name（方法需要时）
Header 与 JSON-RPC body 是否一致
Content-Type / Accept
认证信息
```

推荐逻辑：

```text
HTTP Request
  ↓ validate protocol headers
  ↓ parse JSON-RPC envelope
  ↓ compare header/body routing keys
  ↓ create RequestContext
  ↓ protocol dispatcher
```

Header 与 Body 不一致时拒绝请求并记录安全事件，不能让两层路由看到不同 Method/Tool Name。

## 5. Legacy 兼容边界

Legacy 兼容的目标是服务旧客户端，不是继续让新业务依赖隐式 Session。

允许：

- `initialize`；
- Legacy `Mcp-Session-Id`；
- 旧版 Streamable HTTP Session；
- 兼容期内的 SSE 测试（若 SDK/目标客户端需要）。

不允许：

- 新业务状态只存在 Transport Session；
- Modern 请求降级为内部 Session；
- Control Plane 依赖 Legacy Session；
- 将 Session ID 当作 User/Tenant 身份；
- 为兼容旧客户端复制 Java 项目的完整 Redis Session 架构。

Legacy usage 必须有 Metric：

```text
mcp_requests_total{era="legacy"}
mcp_legacy_fallback_total
mcp_legacy_sessions_active
```

## 6. Application State 与 Protocol Session

Modern MCP 删除协议 Session，不代表业务不能有状态。

需要跨调用的业务状态应显式建模，例如：

```text
approval_id
task_id
cursor
document_id
request_state
```

它们由业务对象或 Extension 管理，而不是隐藏在 Transport Connection 中。

## 7. MRTR 与 Approval

需要用户补充输入或批准时，现代路径优先使用协议允许的 input-required/MRTR 模式或明确的 Approval Resource：

```text
tools/call
  ↓ Policy = REQUIRE_APPROVAL
input_required / approval reference
  ↓ user/host resolve
retry original call with response + request_state
  ↓ re-check policy and execute
```

必须保证：

- `request_state` 防篡改；
- 重试不会绕过 Policy；
- Approval 绑定原始 Principal、Tool 和参数摘要；
- Approval 过期、拒绝和重复提交都有确定行为；
- 非幂等 Tool 不因传输重试被执行两次。

具体 Approval API 是否完全依赖 MRTR，在实现阶段通过 SDK 能力和目标客户端兼容性确认。

## 8. Cache 与 Tool Catalog

`tools/list`、资源列表等结果支持缓存提示时，缓存键至少考虑：

```text
tenant
principal/role visibility
agent
server/tool publish version
policy snapshot
protocol era
```

不能把管理员可见的 Tool Catalog 缓存直接复用于普通用户。

Tool Publish/Disable/Policy Change 应触发缓存失效或版本推进。

## 9. Trace Context

协议链路使用：

```text
traceparent
tracestate
```

`tenant_id/user_id/agent_id` 等业务身份来自已验证 Token Claims 或可信内部 Context，不直接相信客户端自定义 Header。

不在 baggage 中放：

- API Key；
- OAuth Token；
- 完整邮箱/手机号；
- Tool 完整 Arguments；
- 文档正文。

## 10. Authorization 基线

现代 HTTP MCP 的授权设计至少遵循：

- HTTPS；
- OAuth 2.1 / PKCE（需要用户授权时）；
- Protected Resource Metadata；
- issuer validation；
- audience validation；
- inbound token 不透传到 downstream API；
- downstream 使用独立 Credential Binding；
- Client Credential 与 issuer 绑定；
- Secret 不进入模型上下文。

MVP 可以先使用内部签名 Token，但接口和状态模型必须允许后续接入 OIDC/OAuth，不把 API Key Query Parameter 固化进架构。

## 11. 协议验收

完成协议阶段必须证明：

- Modern `server/discover`、`tools/list`、`tools/call` 可运行；
- Legacy `initialize` 和 Session Client 可兼容；
- auto negotiation 可以选择正确时代；
- Header/Body 不一致会被拒绝；
- unknown method 返回规范错误；
- modern request 不创建 Transport Session；
- protocol era 可在 Trace/Metric/Audit 中查询；
- list cache 不跨越权限边界；
- Approval/input-required 路径不会重复执行 Tool。

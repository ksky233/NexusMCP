# S2-2B 持久化基线遇见的问题与解决

> 日期：2026-08-25
> 阶段：PostgreSQL 18.6、SQLAlchemy Async、Alembic Baseline、Integration Test
> 结论：所有问题已解决并进入自动化验证；没有业务数据丢失。

## 1. PostgreSQL 18 Docker Volume 目录变化

### 现象

项目 Container 不断 Restart，日志提示 PostgreSQL 18 使用按主版本区分的数据目录，并拒绝使用旧挂载方式。

最初配置：

```yaml
volumes:
  - postgres_data:/var/lib/postgresql/data
```

### 原因

PostgreSQL 18 官方 Docker Image 将实际 `PGDATA` 放在：

```text
/var/lib/postgresql/18/docker
```

Volume 应挂载其上级目录：

```text
/var/lib/postgresql
```

这样未来执行 Major Upgrade 时，新旧主版本数据目录可以并存，不会跨越 Mount Boundary。

镜像检测到旧路径存在数据时选择拒绝启动，而不是猜测如何迁移，避免误挂载造成数据损坏。

### 修复

```yaml
volumes:
  - postgres_data:/var/lib/postgresql
```

失败 Volume 是本轮刚创建的空资源。确认 Compose Label 后，删除并重新创建：

```text
nexusmcp-postgres-1
nexusmcp_postgres_data
```

已有 `postgres-demo` 明确排除，没有被修改。

### 预防

- 升级数据库 Major Version 前阅读官方 Image 迁移说明；
- Container 和 Volume 使用独立 Compose Project Label；
- 删除 Volume 前验证名称、Label 和数据价值；
- 开发、测试和 CI 固定相同 PostgreSQL Major/Minor Version。

### 位置

- `docker-compose.yml`
- `docker/postgres/init-test-db.sql`

## 2. Alembic 循环 Foreign Key 建表顺序

### 现象

两个模型互相保留引用：

```text
ImportedOperation.draft_tool_binding_id
→ ToolBinding.id

ToolBinding.imported_operation_id
→ ImportedOperation.id
```

形成循环：

```text
ImportedOperation ──→ ToolBinding
       ↑                  │
       └──────────────────┘
```

Alembic Autogenerate 首次将 `draft_tool_binding_id` Foreign Key 直接放进 `imported_operation` 建表语句，但此时 `tool_binding` 尚未创建。

### 原因

如果先创建任意一张表，并在 `CREATE TABLE` 中加入指向另一张表的 Foreign Key，PostgreSQL 都会遇到目标表不存在的问题。

### 修复

延后创建其中一侧 Foreign Key：

```text
1. 创建 imported_operation，不创建该 FK
2. 创建 tool_binding
3. 两张表存在后执行 ALTER TABLE ADD FOREIGN KEY
```

Migration：

```python
op.create_foreign_key(
    "fk_imported_operation_draft_tool_binding_id_tool_binding",
    "imported_operation",
    "tool_binding",
    ["draft_tool_binding_id"],
    ["id"],
    ondelete="SET NULL",
)
```

Downgrade 反向处理：

```text
先删除延后 FK
→ 删除 tool_binding
→ 删除 imported_operation
```

### 预防

- Autogenerate 后必须人工审查 Revision；
- 遇到互相引用时明确一侧使用 Delayed Constraint；
- Upgrade 和 Downgrade 都要在空库真实执行；
- 定期复审双向引用是否真的必要，避免冗余状态。

### 位置

- `src/nexusmcp/modules/openapi_import/adapters/sqlalchemy_models.py`
- `src/nexusmcp/modules/connectors/adapters/sqlalchemy_models.py`
- `migrations/versions/65b188208572_create_initial_registry_and_catalog_.py`

## 3. Constraint 名称过于泛化

### 现象

初始名称包含：

```text
identity
tool_version
job_operation
```

如果 PostgreSQL 报错：

```text
duplicate key violates unique constraint "identity"
```

无法快速判断涉及哪张表、哪些字段和哪条业务不变量。

### 原因

Constraint Name 会进入：

- PostgreSQL Error；
- Alembic Diff/Upgrade/Downgrade；
- Log 和监控；
- Integration Test；
- 故障排查记录。

泛化名称缺少表和字段语义；Index Name 在同一 Schema 内还可能发生重名。

### 修复

统一使用：

```text
类型_表名_关键字段
```

例如：

```text
uq_upstream_service_tenant_namespace_name
uq_tool_tenant_canonical_name
uq_tool_version_tool_version
uq_imported_operation_job_operation
uq_tool_binding_tool_version
```

统一前缀：

```text
pk_  Primary Key
fk_  Foreign Key
uq_  Unique Constraint
ck_  Check Constraint
ix_  Index
```

### 预防

- Declarative Base 设置统一 Naming Convention；
- 显式 Constraint 使用完整稳定名称；
- 命名能够直接翻译成业务不变量；
- 生成 Revision 后检查所有 `pk/fk/uq/ck/ix` 名称。

### 位置

- `src/nexusmcp/infrastructure/persistence/base.py`
- 各上下文 `sqlalchemy_models.py`

## 4. 无 ORM Relationship 时的 Flush 顺序

### 现象

测试将以下对象同时加入 Session：

```text
Tenant
Tool
UpstreamService
ToolVersion
```

然后直接 Commit：

```python
session.add(tenant)
session.add(tool)
session.add(upstream)
session.add(tool_version)
await session.commit()
```

实际先执行了 Tool Insert，PostgreSQL 正确拒绝：

```text
ForeignKeyViolation
Tool.tenant_id 对应的 Tenant 尚不存在
```

### 原因

Model 只有数据库 Foreign Key，没有定义 ORM `relationship()` 对象图。

这是有意设计：

- 避免隐式 Lazy Load；
- 避免跨限界上下文随意遍历 ORM Graph；
- 由 Repository/Use Case 控制业务加载和事务。

但代价是不能依赖 ORM 自动推断实例级业务写入顺序。

### 修复

显式 Flush：

```python
session.add(tenant)
await session.flush()

session.add(tool)
session.add(upstream)
await session.flush()

session.add(tool_version)
await session.commit()
```

`flush` 只把 SQL 发送到数据库，仍在同一事务内；任意后续失败仍可整体 Rollback。

### 预防

- Repository 不自行 Commit；
- 顶层 Use Case/Unit of Work 控制 Flush/Commit 顺序；
- Aggregate Root 和依赖对象按 FK 顺序写入；
- 不依赖 Lazy Relationship 触发业务读取；
- Integration Test 使用真实 Foreign Key 验证顺序。

### 位置

- `tests/integration/persistence/test_postgresql_baseline.py`

## 5. Alembic 环境变量覆盖测试 URL

### 现象

单独运行 PostgreSQL Integration Test 通过，但全量测试同时设置开发库和测试库 URL 时失败：

```text
Alembic 日志显示 Downgrade 成功
测试检查 nexusmcp_test 时表仍然存在
```

### 原因

原始优先级：

```python
database_url = (
    os.getenv("NEXUSMCP_DATABASE_URL")
    or config.get_main_option("sqlalchemy.url")
)
```

全量测试同时存在：

```text
NEXUSMCP_DATABASE_URL = nexusmcp
Alembic Config URL    = nexusmcp_test
```

环境变量优先导致 Test Config 被忽略，Migration 实际操作了开发库；测试断言却读取测试库。

### 修复

显式 Config 优先，环境变量作为普通 CLI Fallback：

```python
configured_url = config.get_main_option("sqlalchemy.url").strip()
database_url = configured_url or os.getenv("NEXUSMCP_DATABASE_URL")
```

新的语义：

```text
程序化调用/Integration Test 显式 URL
> 普通 CLI 环境变量
```

测试再增加保护：

```text
数据库名称必须包含 "test"
Driver 必须是 postgresql+asyncpg
```

### 预防

- 程序化测试使用显式 Config，不依赖全局环境；
- 测试数据库名称必须带 Test 标识；
- 开发库和测试库使用不同 Database；
- 全量测试同时设置两个 URL，覆盖优先级场景；
- 测试结束恢复 Test DB 到 Alembic Head。

### 位置

- `migrations/env.py`
- `tests/integration/persistence/test_postgresql_baseline.py`

## 6. 为什么这些问题有价值

这些问题分别位于不同基础设施边界：

| 问题 | 边界 |
|---|---|
| PostgreSQL 18 Volume |部署/容器 |
|循环 Foreign Key | DDL/Migration |
| Constraint Name |可维护性/可观测性 |
|显式 Flush | ORM Unit of Work |
| URL 优先级 |环境隔离/测试安全 |

只使用 InMemory Repository 或 Unit Test 无法发现它们。

真实验证链：

```text
Docker
→ PostgreSQL 18.6
→ Alembic
→ SQLAlchemy Async
→ asyncpg
→ Integration Test
```

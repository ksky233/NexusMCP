# NexusMCP 持久化模型与发布事务

> 状态：Accepted，作为 S2-2B ORM/Migration 实现输入
> 日期：2026-08-25
> 范围：S2 首批持久化模型、状态机、约束、事务和 Repository 边界
> 不在本文冻结：SQLAlchemy 文件拆分、PostgreSQL 精确镜像版本、S3 Policy/Credential/Audit 表。

## 1. 结论

S2 首批持久化采用：

```text
PostgreSQL
SQLAlchemy 2 Async
Alembic
应用生成 UUID
JSONB
timestamptz
```

Tool 的稳定身份、版本化契约和执行绑定必须分离：

```text
Tool
└── ToolVersion
    └── ToolBinding
```

Tool Definition 继续作为“Agent 可见 Tool 契约”的领域词汇，但不直接对应一张表；代码使用
`PublishedTool` 明确表达运行时只读投影。该投影来自：

```text
Tool Identity
+ Published ToolVersion
+ Published ToolBinding Metadata（不含 Secret）
```

原有内存 `ToolDefinition` 已在 S2-2B-2 拆分为 `Tool`、`ToolVersion` 和 `PublishedTool`，
SQLAlchemy Model 仍只属于 Persistence Adapter。

## 2. 第一批关系

```text
Tenant
├── UpstreamService
│   └── OpenApiImportJob
│       └── ImportedOperation
│
└── Tool
    └── ToolVersion
        └── ToolBinding ──→ UpstreamService
                 └───────→ ImportedOperation（可选来源）
```

基数：

```text
Tenant              1 ── N UpstreamService
UpstreamService     1 ── N OpenApiImportJob
OpenApiImportJob    1 ── N ImportedOperation
Tenant              1 ── N Tool
Tool                1 ── N ToolVersion
ToolVersion         1 ── 1 ToolBinding（S2）
UpstreamService     1 ── N ToolBinding
ImportedOperation   1 ── 0..1 Draft ToolVersion/Binding（S2）
```

## 3. Tool Identity、Version 与 Definition

### 3.1 Tool

Tool 是跨版本稳定身份：

```text
directory.get_employee
```

以下内容属于 Tool：

- Tenant；
- Namespace；
- Canonical Name；
- Owner；
- Active/Disabled 状态。

`namespace` 单独保存为 `directory`，用于检索、治理和来源分组；`canonical_name` 保存完整对外名称 `directory.get_employee`，并在 Tenant 内唯一。

### 3.2 ToolVersion

ToolVersion 是不可变对外契约：

```text
directory.get_employee@1
directory.get_employee@2
```

以下内容属于 Version：

- Display Name/Description；
- Input/Output Schema；
- Schema Digest；
- Tags/Visibility；
- SideEffect；
- Draft/Review/Published/Retired 状态。

### 3.3 PublishedTool Projection

`tools/list` 不应加载整个写模型 Aggregate。Catalog Repository 返回专用 Published Tool Projection：

```text
PublishedTool
- tool_id
- tool_version_id
- tenant_id
- canonical_name
- display_name
- description
- input_schema
- output_schema
- version
- visibility
- side_effect
- schema_digest
```

MCP Adapter 只依赖该 Application Read Model，不依赖 ORM。

## 4. 状态机

### 4.1 UpstreamService

```text
draft → active → disabled
          ↑         │
          └─────────┘（显式重新启用）
```

### 4.2 OpenApiImportJob

```text
pending → validating → parsing → completed
   │           │           │
   └───────────┴───────────┴→ failed
```

Completed Job 不修改其历史 Operation；重新导入创建新 Job。

### 4.3 ImportedOperation Review

```text
pending → accepted
        → rejected
        → needs_change → accepted/rejected
```

### 4.4 ToolVersion

```text
draft → review → published → retired
  │        │
  └────────┴→ discarded（可物理删除未发布 Draft，策略后定）
```

Published Version 不允许回到 Draft/Review。

### 4.5 ToolBinding

```text
draft → published → disabled
```

Version Publish 与 Binding Publish 必须同事务发生。

## 5. Import 事务

### 5.1 为什么拆成多个事务

OpenAPI 读取、解析和 `$ref` 标准化可能耗时，也可能访问文件/网络，不能长时间持有数据库事务。

```text
事务 A
创建 pending ImportJob
提交

事务外
读取 Source
校验/解析/标准化

事务 B
锁定 ImportJob
写入 ImportedOperations
标记 completed
提交
```

失败时使用独立短事务将 Job 标记为 `failed`。

### 5.2 幂等策略

S2 第一版：

- Source Digest 相同不等于禁止新 Job；允许保留多次导入证据；
- 同一 Job 内 `operation_key` 唯一；
- 重复提交可以在 Application 层选择复用最近 Completed Job；
- ImportJob 完成写入采用 Replace-All 或首次写入，禁止产生重复 Operation；
- 具体“复用还是新建”由 Import Command 显式参数决定，不静默猜测。

## 6. Review 与 Draft 事务

当 Operation 被接受时：

```text
锁定 ImportedOperation
→ 校验 Upstream Active、Tenant 一致
→ 创建或查找稳定 Tool Identity
→ 分配下一个 ToolVersion Number
→ 创建 Draft ToolVersion
→ 创建 Draft ToolBinding
→ 回写 Operation 的 Draft IDs
→ 标记 accepted
→ 提交
```

并发规则：

- 分配 Version Number 时锁定 Tool Row；
- `(tool_id, version)` Unique Constraint 作为最终防线；
- 相同 Operation 重复 Review 必须返回已有 Draft 或明确冲突，不创建多个 Draft。

## 7. Publish 事务

### 7.1 前置条件

- ImportedOperation Review 为 `accepted`；
- Tool/Version/Binding 属于同一 Tenant；
- ToolVersion 为 `review`；
- ToolBinding 为 `draft`；
- Upstream 为 `active`；
- Schema/Binding Digest 可重新计算且一致；
- 不存在 Name/Version 冲突。

### 7.2 原子发布

```text
BEGIN
  SELECT Tool FOR UPDATE
  SELECT Draft ToolVersion/Binding FOR UPDATE

  Retire 当前 Published ToolVersion
  Disable/Retire 当前 Published Binding
  Publish 新 ToolVersion
  Publish 新 ToolBinding
  Activate Tool
COMMIT
```

数据库约束保证每个 Tool 最多一个 Published Version。

任何失败必须整体 Rollback，不能出现：

- Published ToolVersion 没有 Published Binding；
- 两个 Published Version；
- Binding 指向其他 Tenant Upstream；
- Tool Active 但不存在 Published Version。

### 7.3 Audit 边界

S2 Publish Use Case 暴露 `ToolPublished` Domain Event/Audit Port，但不宣称 Audit 与发布事务原子。

Audit 同库同步写、Transactional Outbox 或异步 Sink 的最终策略在 ADR-0010 决定。

## 8. Tenant 隔离

- 所有 S2 业务表包含非空 `tenant_id`；
- Repository 方法必须显式接收 Tenant ID；
- 唯一约束包含 Tenant Scope；
- Foreign Key 保证实体存在，Application/Domain 验证关联对象 Tenant 相同；
- Cross-tenant 绑定必须在写入前拒绝并通过 Integration Test；
- PostgreSQL RLS 属于后续加固项，不能替代 Application 层 Tenant 条件。

## 9. Secret 与敏感数据

首批表不得保存：

- API Key/OAuth Token；
- Authorization/Cookie；
- 未知来源完整 Header；
- Tool Call Arguments/Result；
- OpenAPI 中的 Secret Example。

可以保存：

- `auth_scheme` 非敏感描述；
- Security Requirement 名称；
- 后续 `secret_ref`；
- 脱敏 Review Warning。

## 10. Repository 与 Unit of Work

候选 Port：

```text
TenantRepository
UpstreamRepository
OpenApiImportRepository
ToolCatalogRepository
ToolBindingRepository
CatalogUnitOfWork
```

S2 实现规则：

- Domain/Application 只依赖 Port；
- SQLAlchemy Session 生命周期由 Persistence Adapter 管理；
- Commit/Rollback 由顶层 Use Case/Unit of Work 决定；
- Repository 不自行 Commit；
- DB Transaction 不跨越 OpenAPI 读取或 Upstream HTTP；
- InMemory Adapter 与 PostgreSQL Adapter 共享 Port Contract Test。

## 11. 第一批 Migration

第一批 Alembic Revision 只创建：

```text
tenant
upstream_service
openapi_import_job
imported_operation
tool
tool_version
tool_binding
```

不创建：

- Principal/Policy/Credential/Approval/Execution/Audit；
- pgvector；
- Redis；
- Search Embedding；
- Runtime Session 表；
- Demo 业务表。

## 12. ORM 与 Domain 边界

SQLAlchemy Model 是持久化 Adapter，不是 Domain Entity。

```text
SQLAlchemy Row
↕ Repository Mapping
Domain Entity / Application Read Model
```

禁止：

- Domain import SQLAlchemy；
- MCP Adapter 返回 ORM Model；
- Pydantic API Schema 被直接当成 ORM；
- 用 Relationship Lazy Load 隐式驱动业务流程；
- 用 `create_all()` 替代 Alembic。

## 13. 实现顺序

1. ADR-0004 确认 PostgreSQL 主存储；
2. 将当前内存 ToolDefinition 拆成 Tool/ToolVersion/PublishedTool；
3. 加入 SQLAlchemy/Alembic/asyncpg；
4. 建立 Persistence Base、Engine、Session/UoW；
5. 创建第一批 ORM Model；
6. 创建 Alembic Baseline；
7. 编写 Empty DB Upgrade/Downgrade Test；
8. 编写 Tenant/Unique/Publish Transaction Integration Test；
9. 实现 PostgreSQL Catalog Adapter；
10. 让正式 `tools/list` 在 Integration 环境读取 Published Projection。

截至 S2-2B-3，Catalog/Binding PostgreSQL Repository、显式 ORM Mapping、Unit of Work 和
共享 Contract Test 已完成；第 10 项留给 Database Bootstrap 阶段。

S2-2B-4 已完成 Publish 事务：UoW 同时暴露 Catalog、Binding 与 Upstream Repository；Tool Row
串行化同一 Tool 的发布，Version/Binding/Upstream 执行排他读取，旧 Published 状态先在事务内
Retire/Disable，再 Publish 新状态并 Activate Tool。

## 14. 验收

- 空 PostgreSQL 可以 Upgrade 到 Head；
- Baseline 可以在测试环境 Downgrade；
- 跨 Tenant Binding 被拒绝；
- 每个 Tool 最多一个 Published Version；
- Publish 失败不会留下部分 Published 状态；
- Draft/Review/Retired 不出现在普通 Catalog Query；
- InMemory/PostgreSQL Adapter 通过同一 Port Contract；
- Schema/Binding 使用 JSONB，Secret Value 不落库；
- 测试数据库与开发数据库隔离；
- 所有 Schema 变更只通过 Alembic。
